# План фронтенда

Дедлайн хакатона: 26.10.2026 (точное время уточнить). Бриф: FRONTEND_BRIEF.md, правила: docs/SCORING_SPEC.md.

## План (Фаза 0)

1. Контракт API — `docs/openapi.yaml` (этот файл заменяет черновик бэкенда без схем; бэкендер реализует по нему).
2. Фронт живёт в `frontend/`: React + Vite + TypeScript + Tailwind + lucide-react, состояние useReducer + Context, без роутера.
3. API-слой: один интерфейс `CreditApi`, две реализации — мок (localStorage) и fetch к `/api`; выбор через `VITE_USE_MOCK`.
4. Мок повторяет сервер: сам двигает заявку по этапам (1 сек на этап), UI только опрашивает `GET /applications/{id}` раз в 700 мс.
5. `scoring.ts` — чистые функции строго по SCORING_SPEC; тесты Vitest на три эталона и границы (44/45, capacity = 0, 299 999 / 300 000, кассовый разрыв 12 мес).
6. Store: шаг wizard + id текущей заявки сохраняются в localStorage → после перезагрузки шаг восстанавливается.
7. Шаг 1: три демо-профиля + ручной ввод ИНН (поиск в «ЕГРЮЛ», при 404 — ручное заполнение), карточка бизнеса редактируется.
8. Шаг 2: слайдеры суммы и срока, три карточки цели, предварительный платёж, кнопка «Отправить заявку в банк» с Idempotency-Key.
9. Умная лента: боковая колонка, сегмент по компании, «Почему вы это видите», после отказа — `context=rejected`.
10. Шаг 3: вертикальный конвейер ЕГРЮЛ → БКИ → скоринг, shimmer, галочки, прогресс-бар; ветка NEEDS_RECHECK с кнопкой «Повторить».
11. Шаг 4: три исхода (одобрено / встречное / отказ), полоски факторов, подписание кодом 1234 (5 попыток), анимация выдачи.
12. Шапка: «Кредитный кабинет», бейдж статуса, «Сбросить демо»; блок «Мои заявки»; футер-бейдж про синтетические данные.
13. Docker: multi-stage `node:20-alpine` → `nginx:alpine`, прокси `/api` → `backend:8000`, сервис в корневом compose.
14. Документы: APPLICATION_STATES (Mermaid), TEST_SCENARIOS, REVIEW_NOTES, frontend/README, THIRD_PARTY_NOTICES (раздел фронта).
15. Финал: `npm run build`, `npm test`, `npm run lint`, `docker compose up --build`, три сценария руками.

## Допущения (на согласование с бэкендером)

- Деньги — целые рубли, ставка — число в % (19, 21.5, 24). Округление half-up.
- `POST /applications` принимает **всю карточку компании** (её можно править на шаге 1), а не только ИНН.
- Неизвестный ИНН в lookup → 404 `COMPANY_NOT_FOUND`; пользователь заполняет карточку сам.
- При отказе со score < 45 ставка не определена → `rate`, `approved_amount`, платёж = `null` (для «Вектора»).
- Для встречного предложения `decision` сразу содержит платёж и переплату по новой сумме; `accept-offer` только меняет статус.
- Неверный код подписи → 400 `INVALID_SIGN_CODE` с `details.attempts_left`; после 5 ошибок → 429.
- Новый маршрут `POST /applications/{id}/retry` (опционально): выход из NEEDS_RECHECK обратно в конвейер.
- Лента: `GET /feed?segment=…&context=rejected`; ответ содержит готовую подпись `reason` и флаг `synthetic: true`.
- Клиентской авторизации нет: история заявок общая (демо). Банковская роль — по `X-Bank-Token`, после DoD.
- Если фронт и бэк разойдутся в числах, прав `docs/SCORING_SPEC.md`. Эталоны пересчитаны: 97 / 46 → 2 500 000 / 8 → отказ.

## Отступления от брифа (Фаза 1)

- **Node 22 вместо Node 20.** Поддержка Node 20 закончилась в апреле 2026, а в Vitest 3 (последнем для Node 20) есть критические уязвимости (`npm audit`). Поэтому взяты Node 22 LTS, Vitest 5, Vite 7, Tailwind 4: `npm audit` — 0 уязвимостей. В Docker будет `node:22-alpine`.
- **Tailwind 4:** цвета проекта задаются в `src/index.css` (блок `@theme`), а не в `tailwind.config.js`.
- **Мок двигает заявку по времени, без таймеров:** этап вычисляется из «сколько прошло с отправки», поэтому заявка продолжает путь и после перезагрузки страницы.

Первый вариант выглядел шаблонно. Новый визуальный язык — как у банковских сайтов для бизнеса: белая страница, серые плашки без теней, поля с серой заливкой и подписью внутри, поле суммы со слайдером у нижнего края, итоговый блок справа, крупные жирные заголовки, прогресс «Шаг N из 4». ## Редизайн v3 (UX-разбор)

- Вместо счётчика «Шаг N из 4» — карточка «Ваша заявка» справа: путь заявки с уже введёнными данными (компания, сумма и срок, проверка, решение), предварительный платёж и главная кнопка шага. Прогресс и итог читаются одновременно, как корзина в интернет-магазине.
- Служебное (демо-режим, «Сбросить демо») — в тёмной полосе сверху; в шапке — только название и выбранная компания.
- Меньше плашек: демо-компании — список с радиокнопками, цель — переключатель, лента — главная статья + список.
- Меньше текста: описание цели только у выбранной, данные компании — краткая сводка с «Изменить» вместо 7 полей.
- Красный только у главной кнопки и слайдера; выбор — чёрным.

## Изюминка: «Запас прочности» (25.10)

На шаге «Сумма и срок» — шкала месячной выручки: текущие платежи по кредитам, новый платёж (зелёная часть — до предела, красная — сверх) и линия безопасного предела 25%. Под шкалой — прогноз решения по тем же правилам, что у банка (`evaluate()` из SCORING_SPEC): «одобрят / одобрят меньше — до X / откажут: причина», сколько рублей в месяц остаётся до предела или на сколько превышение, и кнопка «Взять X» для суммы, которую одобрят. Ставка в карточке заявки теперь по прогнозу («около 24%»), при прогнозе отказа — «базовая». Код: `features/calculator/marginMath.ts` (расчёт + тесты), `SafetyMargin.tsx` (вид).

## Следующее: рабочее место сотрудника банка (после Фазы 3)

Запрос из практики: менеджеры считают нагрузку и лимиты вручную. Экран «Режим банка»: очередь заявок; по каждой — автоматический расчёт (долговая нагрузка, платёжная способность, максимум, факторы скоринга), сценарии «что если» (другая сумма/срок) и автоматически собранное заключение простым текстом; ручное одобрение/отказ с комментарием (`/bank/...` в контракте). Это правила, а не нейросеть: кейс разрешает только LLM с открытыми весами, а прозрачный расчёт проще проверить и объяснить жюри.
