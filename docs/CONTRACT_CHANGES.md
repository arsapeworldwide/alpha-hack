# Уточнения черновика API — Фаза 2

Фронтенд-контракт не предоставлен. В Фазе 0 существовал только черновой перечень
маршрутов без схем запросов/ответов. Ниже зафиксированы решения бэкенда для
согласования с фронтендом; исходные числа SCORING_SPEC не менялись.

- `docs/openapi.yaml` теперь экспортируется из FastAPI командой
  `python -m scripts.export_openapi` из `backend/` и содержит реализованные маршруты.
- Банковские `GET /api/bank/applications` и
  `POST /api/bank/applications/{id}/decision` остаются в объёме Фазы 4.
  Они пока не реализованы и поэтому отсутствуют в текущей экспортированной схеме.
  До Фазы 4 обращение к ним возвращает общий 404, а не успешную заглушку.
- Тело создания: `{inn, requested_amount, term_months, goal}`. Финансовые показатели
  и кредитная история берутся из синтетического профиля, клиент их не подменяет.
- Первое создание — 201/SUBMITTED. Повтор с тем же Idempotency-Key и телом — 200
  с текущей сохранённой заявкой. Тот же ключ с другим телом — 409/IDEMPOTENCY_CONFLICT.
- ИНН — строка из 10 или 12 ASCII-цифр, без проверки контрольной суммы, поскольку
  обязательные профили синтетические. Неизвестный ИНН в lookup — 200 с found=false,
  company=null и мягким сообщением. Создание заявки для него — 404/COMPANY_NOT_FOUND.
- Списки профилей, истории и ленты — JSON-массивы. История поддерживает limit
  (1–100, по умолчанию 50) и offset (от 0), новые заявки идут первыми.
- Ответ заявки содержит company, parameters, stages, decision, score, factors,
  rejection_reason, recommendations, reapply_date, events и остаток попыток подписания.
- Ставка и баллы факторов — десятичные строки, деньги — целые рубли.
  Времена — ISO 8601 UTC с Z, дата повторной подачи — YYYY-MM-DD.
- 5 неверных четырёхзначных кодов возвращают 400/INVALID_SIGN_CODE и уменьшают
  остаток попыток; после этого любой код, включая верный, возвращает 429.
  Неверный формат кода — 422 и не расходует попытки.
- Недопустимый переход — 409/INVALID_TRANSITION. Ошибки имеют форму
  `{code, message, details}`. Все коды и схемы опубликованы в API_CONTRACT.md и OpenAPI.
- NEEDS_RECHECK — сохранённая заявка без отказа. После выключения режима сбоя
  и перезапуска проверка БКИ автоматически повторяется. GET не запускает побочных действий.
- demo/reset останавливает фоновые задачи, удаляет заявки, события, факторы
  и ключи идемпотентности; компании и материалы ленты сохраняются.

## Фаза 4: банковские маршруты

Оба отложенных банковских маршрута реализованы и включены в экспорт OpenAPI.
Входной контракт сохранён: action=approve|reject и обязательный comment,
доступ по X-Bank-Token. Без верного токена — 401/BANK_UNAUTHORIZED.
Swagger использует APIKeyHeader/BankToken. Форма успешного ответа — ApplicationResponse.

С пользователем явно согласовано: при score <45 ручное одобрение недоступно,
поскольку SPEC не задаёт ставку; возвращается 409/BANK_RATE_UNAVAILABLE.
Ставки и числа SPEC не изменялись. Одобрение без завершённого скоринга —
409/BANK_SCORING_REQUIRED. Ручное approve при score от 45 одобряет исходную
запрошенную сумму по сохранённым score/goal, даже при автоматическом отказе
по capacity или встречном предложении. Финансовый расчёт использует те же формулы SPEC.

Очередь — массив заявок в APPROVED/COUNTER_OFFER/REJECTED/NEEDS_RECHECK,
limit/offset как в истории, порядок по updated_at от старых к новым.
После принятия предложения, подписания и выдачи ручные изменения запрещены.
Банковское подтверждение уже имеющегося решения записывается как событие
без изменения названия статуса; это разрешено только для роли bank.
Комментарий, предыдущие условия и новые условия сохраняются в details.
