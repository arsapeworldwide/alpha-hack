## Логика и данные

Источник чисел — SCORING_SPEC.md. Вычисления через Decimal, денежные результаты
целыми рублями. Баллы сохраняются текстом, потому что SQLite Numeric может
проводить дробь через float. Скоринг и решение не зависят от FastAPI и БД.
Эталоны и границы опубликованы в scoring_cases.json.
Никакой ML или LLM не используется.

Все данные синтетические. ЕГРЮЛ и БКИ — локальные адаптеры таблицы companies
за абстрактными интерфейсами. Код подписания 1234 и выдача — симуляторы.
Нет связи с настоящими реестрами, банком, SMS, почтой и мессенджерами.
Неизвестный ИНН можно проверить, но создать заявку можно только на одну из пяти seed-компаний.
Показатели профиля нельзя подменить в теле создания заявки.
После обновления frontend cebb1d4 пользователь выбрал исключить ручной ввод:
карточка компании только для чтения, неизвестный ИНН не открывает форму.
Поэтому исходные UI-файлы скорректированы в этой части с прямого разрешения пользователя.
Старые UI-черновики v1 не восстанавливаются; серверная история сохранена.
Финальная проверка: 195 pytest и 63 Vitest; добавлен тест подмены финансовых показателей.

## Надёжность и ограничения демо

Каждый переход и событие фиксируются одной транзакцией. Ключ идемпотентности,
его отпечаток запроса и счётчик неверных кодов хранятся в БД.
Заявка возвращается как SUBMITTED до запуска фоновой обработки.
Каждый этап ждёт PIPELINE_STEP_SECONDS вне транзакции; в тестах пауза равна 0.
При остановке asyncio-задачи отменяются, данные остаются в БД.
Промежуточные состояния и SIGNED восстанавливаются при следующем старте.
БКИ при сбое переводит заявку в NEEDS_RECHECK без финансового отказа.
Повтор — кнопкой в интерфейсе (POST retry) либо после выключения сбоя и перезапуска.
При включённом сбое повтор снова вернёт NEEDS_RECHECK. Бесконечных повторов нет.
Непредвиденная ошибка фоновой задачи оставляет этап для восстановления при старте.
Повторная подача после отказа — календарная дата +3 месяца с ограничением последним
днём месяца; дата рассчитывается относительно текущей даты UTC.

Предполагается одна реплика Uvicorn (`--workers 1`). Записи короткие и синхронные:
общий asyncio.Lock упорядочивает изменения, подписание и reset внутри процесса.
Оптимистическая версия строки выявляет конфликт обновления, но не заменяет
координацию фоновых задач между процессами. Несколько API-воркеров сейчас не поддерживаются.
SQLite использует WAL, внешние ключи и ожидание блокировки.
Seed дополняет отсутствующие данные и не затирает существующие строки.
Схема создаётся через create_all; изменения существующих таблиц требуют миграций.
P1 добавляет отдельные таблицы доступа и демо-режима, не меняя applications.

## Безопасность и наблюдаемость

В P1 реализованы серверные сессии, роли и изоляция по компании. Пароли хешированы,
в БД хранится хеш токена; выход отзывает сессию, вход ограничивает неверные попытки.
Reset и пульт доступны только директору демо-группы/банку и только в DEMO_MODE.
Сотрудник входит по своей учётке, reviewer записывается в банковское событие.
X-Bank-Token оставлен только для совместимости демо и не идентифицирует сотрудника.
DEMO_MODE=false блокирует демо-учётки и их старые сессии. Это прототип доступа:
для реальных данных нужны промышленный IdP, администрирование и общий rate limiter.
Ответы ошибок единообразны и не содержат traceback или исходных неверных значений.
Журнал статусов хранится отдельно; в логах запросов только шаблон маршрута,
метод, статус, request-id и длительность. Коды, ИНН, тело и query string не пишутся.
Стандартный access-log Uvicorn отключён в приложении и командах запуска.
Swagger использует локальные JS/CSS с отключённым удалённым валидатором.

## Контейнеризация и фактическая проверка

backend/Dockerfile использует python:3.12-slim и runtime-lock с хешами.
Необходимы бинарные wheels; зависимости разрешаются для Linux amd64 и arm64
с glibc >=2.28. Контейнер запускается как 10001:10001, rootfs только для чтения,
capabilities сброшены. /data доступен на запись через named volume; права каталога
создаются в образе для UID 10001. Healthcheck вызывает API и проверяет соединение с БД.
Compose запускает frontend и backend; по умолчанию VITE_USE_MOCK=false.
Инструкция nginx — FRONTEND_INTEGRATION.md; frontend/ совпадает с origin/frontend.

Официальный Compose 2.35.1 подтвердил корректность конфигурации. При первом прогоне
Docker Engine и WSL отсутствовали; compose up --build не нашёл docker_engine.
После разрешения пользователя установлены Docker Desktop 4.96.3 и WSL 3.0.3.
Windows потребовала перезагрузку для включённой Virtual Machine Platform;
пользователь перезагрузил ПК и запустил Docker Desktop. Перезагрузка автоматически не выполнялась.
После этого compose up --build --wait собрал образ и поднял healthy-контейнер.
Подтверждены UID/GID 10001, запись в volume /data и отсутствие записи в /app.
Первоначальный CLI остаётся в игнорируемой .tools/; теперь также установлены
системные Docker CLI 29.9.2 и Compose 5.6.1 через официальный пакет winget.
Все три сценария прошли по HTTP в контейнере с паузой 1 секунда;
scripts/smoke_api.py --verify-report подтвердил прежние ID и результаты после restart.
После включения SIMULATE_BKI_FAILURE заявка попала в NEEDS_RECHECK, а после
выключения сбоя и пересоздания контейнера с тем же volume дошла до APPROVED.
Повтор БКИ отражён в журнале, факторы не дублируются.
POST /demo/reset удаляет заявки, события и факторы, сохраняя 5 компаний, 3 демо-профиля и 31 статью ленты (19 по сегментам + 3 совета после отказа в каждом из 4 сегментов).
Swagger и локальные ресурсы доступны через /api/docs.
Отдельный read-only контейнер с --network none прошёл health и три исхода скоринга;
доступ к интернету в рантайме не потребовался. Запуск проверен на linux/amd64.

## Ручное решение банка

Банк получает очередь полных заявок с факторами в APPROVED/COUNTER_OFFER/REJECTED/NEEDS_RECHECK.
До принятия предложения клиентом сотрудник может принять решение с необязательным комментарием до 500 символов.
Статус, условия, decision.decided_by=bank и событие actor=bank сохраняются одной транзакцией,
в событии остаются предыдущие условия. Комментарий доступен клиенту и не является
внутренней банковской заметкой. Подтверждение того же решения тоже попадает в журнал.
Общий lock сериализует ручное решение и подпись: оба конфликтующих действия не могут завершиться успешно.
Ручное решение переживает перезапуск и не перезаписывается автоматическим конвейером.

Ручное approve одобряет исходную запрошенную сумму по ставке SPEC для сохранённого
score и goal; фактор capacity может быть перекрыт сотрудником, score и факторы не меняются.
Это демонстрационное допущение: в промышленном банке нужны лимиты полномочий,
подтверждающие документы и отдельная политика ручного андеррайтинга.
С пользователем явно согласовано: score <45 не одобряется вручную (409),
так как в SPEC отсутствует ставка. Без завершённого скоринга одобрение также недоступно.
Показатели и числа автоматического скоринга не изменены.
После OFFER_ACCEPTED, SIGNED и DISBURSED, а также во время автоматических проверок — 409.
Ручное решение не сбрасывает счётчик попыток подписания.
