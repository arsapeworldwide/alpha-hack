# Примечания для ревью

Прототип покрывает путь от заявки до демонстрационной выдачи, ручное решение банка
и запрос документов. Основной запуск — Docker Compose с SQLite; PostgreSQL 16
доступен через overlay. [Сценарии](TEST_SCENARIOS.md) и [проверка версии](DEMO_FIXES_RESULTS.md)
описывают воспроизведение. Правила API — в [контракте](API_CONTRACT.md).

## Расчёт и объяснимость

Источник чисел — [SCORING_SPEC](SCORING_SPEC.md), общие эталоны —
[scoring_cases.json](scoring_cases.json). Domain-функции не зависят от FastAPI и БД;
ML/LLM не используется. Расчёты — int/Decimal, денежные результаты в целых рублях.
Баллы факторов сохраняются строками Decimal, чтобы SQLite не проводил дробь через float.

Месячный платёж округляется half-up. Переплата считается от округлённого месячного
платежа, как в интерфейсе: payment × term − amount. Для двух положительных эталонов
это 3 196 160 ₽ и 1 030 952 ₽; баллы трёх профилей — 97/46/8.
Встречная сумма округляется вниз до 100 000 ₽ после расчёта максимума.

Данные компании берутся из seed-реестра; ручной ввод отключён для защиты показателей
скоринга. Подмена полей запроса не меняет реестровые значения. В заявке сохраняется
снимок использованных данных. Неизвестный ИНН не позволяет создать заявку.

## Что смоделировано

Все данные синтетические; ИНН могут случайно совпасть с реальными.
ЕГРЮЛ и БКИ — локальные адаптеры за абстрактными интерфейсами. Подписание кодом
1234 и выдача — переходы состояний, реальные деньги не переводятся.
Нет связи с настоящими реестрами, банком, SMS, почтой или мессенджерами.
Swagger использует локальные JS/CSS, основной сценарий не требует интернета.

До согласия публичные lookup/demo-profiles не возвращают кредитную историю и платежи.
POST заявки требует consent=true, время согласия сохраняется в БД и журнале.
После него конвейер обращается к симуляторам. Неизвестные значения в браузере — null.

Три продукта используют ставки SPEC. Крупная сумма по лимитам продукта или рейтинг C
при сумме к выдаче выше 5 млн направляется в MANUAL_REVIEW. Клиент ждёт специалиста,
банк видит автоматическую рекомендацию. Три исходных эталона остаются прежними.

INFO_REQUESTED содержит чек-лист документов. Директор загружает PDF/PNG/JPEG до 10 МиБ
с согласием; бухгалтер может просматривать и скачивать. Проверяются размер, MIME
и сигнатура, файл хранится под случайным именем, SHA-256 и метаданные — в БД.
После полного списка повторяются прежние проверки. OCR, ФНС, антивирус и проверка
подлинности не реализованы; содержимое файла не меняет показатели компании.

## Надёжность и данные

Статус и событие сохраняются одной транзакцией. Идемпотентность, отпечаток запроса,
счётчик неверных кодов и банковские решения хранятся в БД. POST возвращает SUBMITTED
до запуска фоновой обработки. Пауза PIPELINE_STEP_SECONDS проходит вне транзакции.
При остановке задачи отменяются; на старте промежуточные статусы и SIGNED дозапускаются.

Сбой БКИ даёт NEEDS_RECHECK без финансового отказа. Повтор — через retry или при
старте с работающим БКИ. Пульт сохраняет режим в БД: рестарт сам по себе сбой не выключает.
Бесконечных повторов нет. Непредвиденная ошибка оставляет этап для восстановления.

Одна реплика Uvicorn и asyncio.Lock упорядочивают изменения. Версия строки обнаруживает
конфликт, но не координирует фоновые задачи между процессами. Несколько API-воркеров
пока не поддерживаются, в том числе с PostgreSQL. SQLite использует WAL и foreign keys.
Seed дополняет компании, продукты и роли, обновляет ленту, не затирает заявки.

Alembic при старте создаёт недостающие таблицы и расширяет CHECK статусов старой SQLite,
сохраняя числовые ограничения. После переноса проверяется foreign_key_check.
Миграция проверена unit-тестом и на копии БД. Перед обновлением нужна резервная копия;
восстановление — из бэкапа, destructive downgrade не выполняется. PostgreSQL overlay
создаёт отдельную БД, автоматического импорта SQLite нет.

## Доступ, банк и аудит

Серверные сессии: случайный токен, в БД его SHA-256; пароли — salted PBKDF2-SHA256.
Выход отзывает сессию. Доступ по memberships изолирует компании; бухгалтер не подписывает.
Reset и демо-пульт доступны директору демо-группы/банку при DEMO_MODE=true.
DEMO_MODE=false блокирует демо-учётки и их старые сессии. Это демонстрационная
схема доступа; для реальных данных нужны IdP, администрирование и общий rate limiter.

Банк может approve/reject/counter/request_info до принятия предложения клиентом.
Counter задаёт свои сумму/срок в границах SPEC; ставка определяется по score и goal.
Превышение capacity требует комментария-обоснования. Score <45 не одобряется (409):
SPEC не задаёт ставку. Без завершённого скоринга одобрение также недоступно.
Второго сотрудника для подтверждения исключений пока нет.

Банковское событие содержит reviewer, прежние условия, новые условия и комментарий.
Комментарий видит клиент; это не внутренняя заметка. Исходные score и факторы сохраняются,
а срок ручной оферты хранится отдельно от исходного срока заявки. После полной загрузки
документов автоматический перерасчёт использует исходные условия заявки.
После OFFER_ACCEPTED/SIGNED/DISBURSED пересмотр запрещён. Счётчик подписи не сбрасывается.

Ошибки единообразны, без traceback и исходных неверных значений. В логах — метод,
шаблон маршрута, статус, request-id и длительность; тела, код подписи и query string
не пишутся. CORS ограничен origin, настройки и секреты читаются из env.

## Проверка, контейнеры и сопровождение

Для версии demo-2026-10-25 прошли 227 pytest, 70 Vitest, ruff/format, ESLint и build.
HTTP и браузерные прогоны проверили три исхода, роли, банк, документы, ручное
рассмотрение, сбой БКИ, reset и сохранение данных после restart на SQLite/PostgreSQL.
Исходная схема docs/frontend/openapi.yaml остаётся контрольным артефактом тестов;
текущий OpenAPI экспортируется из FastAPI и проверяется на полное совпадение.

Runtime-lock фиксирует версии и хеши. Python-контейнер работает как UID/GID 10001,
rootfs только для чтения, capabilities сброшены; /data — постоянный volume,
/tmp — tmpfs. Healthcheck проверяет API и БД. Лицензии 37 Python-пакетов,
Swagger, PostgreSQL и других компонентов — в [THIRD_PARTY_NOTICES](../THIRD_PARTY_NOTICES.md).
Дополнительный публичный туннель зависит от сети и работающего хоста.

## Продуктовая проверка и развитие

[Гипотезы H1–H5](HYPOTHESES.md) связывают роли, функции и метрики;
полевые интервью запланированы по [CustDev](CUSTDEV.md). По наблюдениям будут
уточняться объяснения, документы, передача действий и банковская очередь.

Для масштабирования: очередь и отдельные воркеры с арендой задачи, идемпотентными
этапами, ограниченными повторами и transactional outbox. Далее — SSO/RBAC,
защищённый аудит с политикой хранения, метрики этапов/очереди, tracing и алерты.
Реальные адаптеры потребуют таймаутов, схем ошибок и правил деградации.
