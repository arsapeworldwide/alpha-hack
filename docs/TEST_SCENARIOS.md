# Сценарии проверки

Все данные синтетические. Нужны Docker с Linux-контейнерами и Compose 2+.
Из корня: `docker compose up --build --wait`, затем `docker compose ps` — healthy.
Swagger: http://localhost:8000/api/docs. Материалы REST Client: api_collection/backend.http.
При первичной сборке нужны интернет и доступ к реестру образов/PyPI; рантайм локальный.

## Три эталонных исхода

В интерфейсе http://localhost:8080 выберите демо-профиль и сумму 10 000 000.
Для API получите компанию через lookup и передайте её в company; requested_amount=10000000,
сроком 36 и goal=working_capital. Ожидается 201/SUBMITTED.
Опросите GET /api/applications/{id} спустя примерно 4 секунды.

| ИНН | Score | Решение | Ставка | Сумма | Платёж | Переплата |
|---|---|---|---|---|---|---|
| 7712345678 | 97 | APPROVED | 19% | 10 000 000 | 366 560 | 3 196 160 |
| 500100732259 | 46 | COUNTER_OFFER | 24% | 2 500 000 | 98 082 | 1 030 952 |
| 7723456789 | 8 | REJECTED | нет | нет | нет | нет |

У всех заявок видны пять факторов, этапы с временами и последовательные события.
Числа также опубликованы в scoring_cases.json, деньги — целые рубли.
У Вектора причина — «Высокая долговая нагрузка», 2–3 рекомендации и дата +3 календарных месяца.

Для APPROVED вызовите POST /api/applications/{id}/sign с {"code":"1234"}:
ответ SIGNED, через ~1 секунду GET вернёт DISBURSED.
Для COUNTER_OFFER сначала вызовите accept-offer, затем sign.
Прямая подпись COUNTER_OFFER или REJECTED — 409.
У отказа поле decision присутствует, но финансовые условия равны null.

## Ошибки и идемпотентность

- Повторите создание с одинаковым Idempotency-Key и телом: 200 и прежний ID.
  Измените срок при том же ключе: 409/INVALID_TRANSITION (details.reason=IDEMPOTENCY_CONFLICT).
- Для готовой к подписанию заявки отправьте пять раз code=0000: первые четыре — 400, пятый — 429,
  остаток уменьшается до 0. Следующий запрос даже с 1234 — 429.
- ИНН «123» — 422 с понятным сообщением. Неизвестный 0000000000 в lookup — 404/COMPANY_NOT_FOUND; создание заявки для него — 404/COMPANY_NOT_FOUND.
- Сумма 299999, сумма 15000001, срок 37, cash_gap/13 — 422.
  cash_gap/12 и сумма 1 000 000 для 7712345678 дают 21%, платёж 93 114, переплату 117 368.
- GET /api/feed?segment=services — четыре синтетических материала;
  при context=rejected первыми идут долговая нагрузка и кредитная история.

## Перезапуск и сброс

Из backend/ своим Python 3.12 запустите:

```sh
python -m scripts.smoke_api --report data/smoke-report.json
```

Скрипт проверяет три сценария и оставляет заявки в БД. Из корня:
`docker compose restart backend`, затем `docker compose up --wait --no-build --pull never`.
Из backend/: `python -m scripts.smoke_api --verify-report data/smoke-report.json`.
Проверяются те же ID, статусы и финансовые результаты. Также можно перезапустить
во время CHECKING_BKI: этапы дозапускаются, результаты и события не дублируются.
POST /api/demo/reset должен удалить заявки, события и факторы; три профиля
и 16 материалов остаются. После reset старые ID из отчёта больше не существуют.

## Недоступность БКИ

В корневом `.env` задайте SIMULATE_BKI_FAILURE=true и выполните
`docker compose up -d --force-recreate --wait backend`.
Новая заявка остановится в NEEDS_RECHECK с сообщением, без финансового отказа.
Верните false и повторите команду — заявка дозапустится из сохранённого состояния.
Обычный restart не применяет новые env. Volume при пересоздании сохраняется.

## Банковская роль

В Swagger нажмите Authorize и введите demo-bank-token (или свой BANK_API_TOKEN).
Альтернатива: заголовок X-Bank-Token в коллекции. Без токена/с неверным токеном — 401.

1. Создайте новую заявку ИП Иванов и дождитесь COUNTER_OFFER.
2. GET /api/bank/applications должен показать её с факторами и журналом.
3. POST /api/bank/applications/{id}/decision с
   {"action":"approve","comment":"Дополнительные данные проверены в демо"}.
4. Ожидается APPROVED, decision.decided_by=bank, decision.score=46 и прежние факторы;
   одобрена исходная сумма 10 000 000 под 24%, платёж 392 329, переплата 4 123 844.
5. В последнем событии actor=bank, комментарий и прежнее предложение 2 500 000.
   Клиент теперь может подписать сразу. После принятия/подписания банк получает 409.
6. В отдельной заявке с автоматическим APPROVED отправьте reject с комментарием:
   статус REJECTED, финансовые поля очищены, причина ручного отказа и рекомендации видны.
7. Для Вектора approve даёт 409/INVALID_TRANSITION (details.reason=BANK_RATE_UNAVAILABLE): SPEC не задаёт ставку при score <45.
   Ручной отказ для NEEDS_RECHECK допустим, одобрение без скоринга — 409/INVALID_TRANSITION (details.reason=BANK_SCORING_REQUIRED).
8. Повторите решение после перезапуска контейнера: ручной результат и журнал сохраняются.
   Во время автоматического конвейера ручное решение — 409.

Ручное одобрение может перекрыть ограничение capacity, но не придумывает ставку.
Это демонстрация банковской роли, не реальные полномочия сотрудника и не выдача денег.

Автоматизация из backend/: `python -m scripts.smoke_bank --report data/bank-report.json`.
После restart и healthy: `python -m scripts.smoke_bank --verify-report data/bank-report.json`.
Для нестандартного токена задайте BANK_API_TOKEN в окружении скрипта.

## Фактическая проверка и ограничения

Обновление frontend cebb1d4: кнопки «Назад к компании», «Отменить и изменить условия»
и «Изменить условия» сохраняют компанию и параметры. Повторная отправка создаёт
новую заявку с новым Idempotency-Key; прежняя остаётся в истории.
После ручной правки выручки подпись риска пересчитывается; «Вернуть исходные данные»
восстанавливает демо-профиль. Автоматизация: tests/e2e/frontend-update.cjs.
Новая версия фронтенда проходит 63 теста Vitest, ESLint и production build.
Источник данных для решения при ручной правке ещё согласуется с пользователем:
прогноз фронтенда использует введённые значения, сервер пока сохраняет прежнюю
проверку по seed-реестру. Этот режим не входит в перечисленные успешные прогоны.

Фаза 3 проверена на Linux/amd64: Docker Desktop 4.96.3, Engine 29.9.2, Compose 5.6.1.
Контейнер healthy, UID/GID 10001, /data доступен на запись, rootfs только для чтения.
Пройден запуск отдельного контейнера с --network none и три исхода скоринга.
Интерфейс и nginx проверены в Edge с реальным API. Три исхода, подпись, reload, reset и сбой БКИ прошли; см. tests/e2e/README.md.
В Фазе 4 обновлённый образ также прошёл scripts/smoke_bank; после restart
подтверждены сохранение ручных решений, ставок, платежей и аудита.
Локальные pytest: 194 теста прошли, ruff и полное сравнение OpenAPI прошли.
Дополнительно оба HTTP-прогона прошли через отдельный nginx 1.30.6 из
docker-compose.integration.yml: проверены /api, банковский токен, CORS,
X-Request-ID, полное совпадение OpenAPI и локальные ресурсы Swagger.
