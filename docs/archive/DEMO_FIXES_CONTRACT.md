# Исправления после проверки стенда

Основание: FIXES_AFTER_DEMO_SOURCE.md и CHANGES_SOURCE.md.
Актуальный контракт зафиксирован в [API_CONTRACT.md](../API_CONTRACT.md).

## Совместимость API

- POST /api/applications теперь требует `consent: true`; отсутствие, false и неверный тип — 422.
  Согласие фиксируется с UTC-временем в application_workflows и в событии SUBMITTED.
- Публичные lookup/demo-profiles возвращают только реестровые поля. Кредитной истории
  и платежей в этих ответах нет. Неизвестные данные браузер хранит как null, не как 0/fair.
  После согласия приложение по-прежнему перепроверяет компанию и запрашивает симулятор БКИ.
- В заявке можно указать WORKING_CAPITAL / INVEST / OVERDRAFT; без кода продукт определяется
  по прежнему goal. Сумма и срок проверяются на сервере по выбранному продукту.
- GET /api/products возвращает три продукта. Ставки 19 / 17 / 21% прежние, надбавки — SPEC.
  Овердрафт ограничен 5 млн / 12 мес из ранее предложенного каталога; другие продукты —
  15 млн / 36 мес, минимумы 300000 и 3 мес. Новая ставка EXPRESS не добавлялась.
- Банковский action: approve / reject / counter / request_info. Для counter обязательны
  amount и term_months; ставка вычисляется сервером. Исходные параметры заявки не затираются,
  фактический срок оферты хранится в журнале и возвращается в decision.term_months.
- Если платёж превышает capacity, обоснование в comment обязательно (422 при отсутствии).
  Предупреждение показывает превышение в ₽/мес. Score <45 по-прежнему запрещает одобрение.
- GET /api/bank/applications?view=needs_decision показывает COUNTER_OFFER, NEEDS_RECHECK,
  MANUAL_REVIEW; view=all — все статусы. Старый view=reviewable оставлен по умолчанию
  для совместимости запросов. В интерфейсе по умолчанию «Требуют решения».
- Банковский ответ дополнен system_recommendation, waiting_minutes, capacity_excess,
  policy_rate. Рекомендация считается по исходным параметрам и отличается от ручной оферты.

## Новые ветки

При автоматическом скоринге сумма к выдаче выше лимита 12 млн для оборотного продукта
или 5 млн для оборудования/овердрафта переводится в MANUAL_REVIEW. Также туда уходит
рейтинг C при сумме к выдаче выше 5 млн. Это правила из CHANGES_SOURCE.md, не новая формула
скоринга. Клиент не видит автоматическую рекомендацию как готовое решение; банк видит её
в карточке и принимает решение. Три исходных эталона не попадают под новые ограничения.

request_info с непустым checklist переводит неподписанную заявку в INFO_REQUESTED.
Клиент видит список. Бухгалтер может смотреть/скачивать свои документы, загрузка — только директору.

POST /api/applications/{id}/documents: multipart kind, file, consent=true.
PDF/PNG/JPEG, до 10 МиБ. Проверяются MIME и сигнатура, файл хранится под случайным именем
в DOCUMENT_DIRECTORY, в БД — тип, размер и SHA-256. Исходное имя и путь клиента не используются.
Неверный тип/сигнатура/отсутствие согласия — 422, превышение размера — 413.
После полного списка заявка возвращается в существующий конвейер ЕГРЮЛ → БКИ → скоринг.
Повторный расчёт удаляет старые факторы перед вставкой новых, не дублирует баллы.
Новое автоматическое решение использует исходный срок, а не срок прежней ручной оферты.

GET /api/applications/{id}/documents/{document_id} и аналогичный /api/bank/applications/...
отдают вложение только при надлежащих правах, с no-store и nosniff. Чужая заявка/файл — 404.
Reset удаляет и метаданные, и связанные файлы. Пользовательские файлы в git не попадают.

Это локальная симуляция: содержимое выписки не извлекается и не подменяет финансовые
данные реестра. Антивирус, OCR, ФНС, второй голос и подтверждение подлинности — вне прототипа.

## Миграции и запуск

Alembic 0001 создаёт недостающие таблицы и расширяет CHECK-ограничения статусов в старой
SQLite. Во время пакетного переноса foreign_keys временно выключены, затем включены;
выполняется foreign_key_check. Числовые ограничения старых таблиц сохраняются.
Миграция проверена на копии фактической БД стенда и отдельным тестом. Резервная копия
до обновления лежит в /data/backups/pre-demo-fixes.db, в git не публикуется.
Downgrade с удалением данных не выполняется: восстановление — из бэкапа.

Обычный compose остаётся на SQLite. PostgreSQL 16 включается отдельным overlay:
`docker compose -f docker-compose.yml -f docker-compose.postgres.yml up --build --wait`.
Это чистая отдельная БД: автоматического переноса данных SQLite в PostgreSQL нет.
Проверка на отдельном compose-проекте не меняет БД действующего SQLite-стенда.

Перед показом: `docker compose ps`, health → ok,
`docker compose exec -T backend python -m app.preflight`.
Перезапуск backend не сбрасывает сохранённый режим БКИ: нужен «Восстановить БКИ» или reset.
Основной способ запуска — Docker на локальном ПК; публичная ссылка —
дополнительный демо-стенд через временный туннель.
