## 1. Авторизация и роли (критерий «Enterprise»)

**Бэкенд**
- `POST /api/auth/login {login, password}` → `{access_token, user}`; `GET /api/auth/me`.
- JWT (`pyjwt`), пароли — `bcrypt`. Секрет — env `JWT_SECRET` (≥ 32 байта).
- Таблицы `users (id, login, password_hash, role, full_name)`, `memberships (user_id, company_inn)`.
- Роли: `client_owner`, `client_accountant`, `underwriter`, `senior_underwriter`.
- Клиент видит только заявки своих компаний; чужая заявка → **404** (не раскрываем существование).
- `accept-offer`, `sign`, `cancel` — только `client_owner`, иначе **403 FORBIDDEN**.
- `/api/bank/*` — только банковские роли. Удалить `X-Bank-Token` / `BANK_API_TOKEN`.
- Лимит **неудачных** входов: 10/мин с IP → 429.
- Seed-учётки: директор и бухгалтер «Альфа Ритейл», директор каждой персоны, `underwriter`, `senior`. Один тестовый пароль в seed-файле, в БД только хеш.

**Фронтенд**
- Экран входа с карточками **«Войти как …»** (персона + сценарий) и формой логин/пароль.
- `GET /api/demo-profiles` отдаёт персоны (логин, роль, компания, сценарий). **Только при `DEMO_MODE=true`.**
- Токен в `localStorage`, при 401 — назад на вход. Кнопка «Выйти».
- Бухгалтер видит заявку, но вместо «Подписать» — «Подписать может руководитель».

**Готово, когда:** бухгалтер получает 403 на подпись; клиент A не видит заявку клиента B; без токена `/api/applications` → 401.

## 2. Экран банка (критерии «Целостность», «UX» — кейс стр. 6)

**Бэкенд**
- `GET /api/bank/applications` — очередь: статусы `MANUAL_REVIEW`, `INFO_REQUESTED`, `NEEDS_RECHECK`; поля: компания, продукт, сумма, срок, сколько ждёт (мин), просрочен ли SLA, причины ручного рассмотрения, рекомендация системы, балл, кто взял в работу.
- `GET /api/bank/applications/{id}` — карточка: всё, что видит клиент + сырые ответы источников, рекомендация системы, журнал событий, журнал обращений к источникам.
- `POST /api/bank/applications/{id}/assign` — «взять в работу».
- `POST /api/bank/applications/{id}/decision` — `{action: approve | counter | request_info | reject, amount?, term_months?, rate?, reason_code?, checklist?, comment?}`.
  - Сумма/срок — в границах продукта, ставка ≥ базовой ставки продукта (иначе 422).
  - `reject` требует `reason_code` из справочника (`GET /api/bank/reason-codes`).
  - **Четыре глаза:** если решение расходится с рекомендацией системы — обязателен `comment`, решение ждёт подтверждения; `POST .../confirm` — только `senior_underwriter` и не тот же сотрудник.
- Оптимистическая блокировка (`version`) — два андеррайтера не перезапишут друг друга (409).

**Фронтенд** (без новых зависимостей, маршрут в хэше: `#/`, `#/app/ID`, `#/dashboard`)
- Очередь (обновляется каждые 2 с), карточка, форма решения, блок «Ждёт второго голоса».
- Клиентский экран при `MANUAL_REVIEW` опрашивает сервер и **сам** обновляется после решения андеррайтера. Комментарий банка показывается клиенту.

**Готово, когда:** персона «Северный Цех» уходит андеррайтеру; он предлагает другую сумму с комментарием; старший подтверждает; у клиента в соседней вкладке появляется предложение без перезагрузки.

## 3. Статусы v2, этап ФНС, стоп-факторы, ручное рассмотрение (кейс стр. 13–15)

**Новые статусы** (одна таблица переходов в `backend/app/domain/state_machine.py` и `frontend/src/api/stateMachine.ts`):

```
SUBMITTED → CHECKING_EGRUL → CHECKING_FNS → CHECKING_BKI → SCORING
CHECKING_EGRUL → REJECTED (стоп-фактор) | MANUAL_REVIEW (нет в реестре) | NEEDS_RECHECK
CHECKING_FNS   → REJECTED (стоп-фактор) | INFO_REQUESTED | NEEDS_RECHECK
CHECKING_BKI   → REJECTED (стоп-фактор) | NEEDS_RECHECK
SCORING        → APPROVED | COUNTER_OFFER | REJECTED | MANUAL_REVIEW
NEEDS_RECHECK  → CHECKING_* (retry) | MANUAL_REVIEW (3-я неудача)
INFO_REQUESTED → CHECKING_FNS (документы загружены) | EXPIRED | CANCELLED
MANUAL_REVIEW  → APPROVED | COUNTER_OFFER | INFO_REQUESTED | REJECTED
APPROVED / COUNTER_OFFER → … | CANCELLED | EXPIRED (оферта 30 дней)
```

**Источники вместо данных клиента**
- Клиент присылает только: `inn, product_code, goal, requested_amount, term_months, declared_revenue?, consent: true`.
- ЕГРЮЛ → название, статус, дата регистрации (→ возраст), ОКВЭД (→ сегмент).
- ФНС (новый симулятор) → выручка, налоговая задолженность.
- БКИ → платежи по кредитам, просрочки. `credit_history` **вычисляется**: просрочка ≥ 30 дн. за 24 мес → `poor`; история < 12 мес или просрочки 1–29 дн. → `fair`; иначе `excellent`.
- АБС (внутренние данные банка) → клиент ли банка, обороты.
- Запрос в БКИ без `consent` невозможен (как в жизни).

**Стоп-факторы** (срабатывают на этапе, где пришли данные; скоринг не выполняется):

| Код | Условие | Этап |
|---|---|---|
| SF_LIQUIDATION | статус «ликвидация»/«банкротство» | ЕГРЮЛ |
| SF_TOO_YOUNG | бизнесу < 3 мес (повтор — дата регистрации + 3 мес) | ЕГРЮЛ |
| SF_TAX_DEBT | налоговый долг > 300 000 ₽ | ФНС |
| SF_OVERDUE_90 | текущая просрочка ≥ 90 дн. | БКИ |

**Ручное рассмотрение (`MANUAL_REVIEW`)**, если:
- сумма к выдаче > лимита авто-решения продукта;
- рейтинг C и сумма к выдаче > 5 млн;
- компании нет в ЕГРЮЛ;
- отказ по нагрузке, но клиент банка ≥ 12 мес с оборотами ≥ 80% месячной выручки;
- 3 неудачных retry источника.

Автоматический расчёт сохраняется как рекомендация системы и показывается только банку.

**Рейтинг** к баллу: ≥ 80 — A, 60–79 — B, 45–59 — C, < 45 — D (границы совпадают с надбавками SPEC).

**Скоринг SPEC v1 не меняется** — меняется только откуда берутся входы. Seed для трёх эталонных ИНН должен давать те же значения, что сейчас.

**Новые персоны** (добавить в seed и в `scoring_cases.json`):

| Персона | Запрос | Ожидание |
|---|---|---|
| ООО «Альтаир» (ликвидация) | любой | REJECTED SF_LIQUIDATION на этапе ЕГРЮЛ |
| ООО «Северный Цех» | оборудование 8 млн / 36 | MANUAL_REVIEW (выше лимита 5 млн) |
| ООО «Опт-Сервис» | оборотный 5 млн, указанная выручка вдвое выше ФНС | INFO_REQUESTED → загрузка выписки → APPROVED |
| ИП Соколова | экспресс 2 млн / 12 | APPROVED автоматически |

Базовые ставки для текущих целей совпадают со SPEC → эталоны не меняются.

- `GET /api/products`, `POST /api/products/recommend {goal, amount, urgent}` → 1–2 продукта с полем «почему подходит» (срочно и ≤ 3 млн → экспресс первым).
- `GET /api/companies/lookup?inn=` — ЕГРЮЛ + выручка ФНС + «клиент банка».
- **Фронтенд:** шаг 1 = «Мы уже знаем о вашей компании» — данные только для чтения, у каждого факта подпись источника; **убрать** ручные поля выручки, платежей, кредитной истории. Шаг 2 = «Для чего деньги?» + «Как срочно?» → карточки продуктов → слайдеры в границах продукта → необязательное поле «актуальная выручка» → чекбокс согласия на запрос в БКИ.
- «Запас прочности» считать по выручке ФНС и подписать «предварительно, текущие кредиты банк узнает в БКИ».
- **Убрать** браузерный мок и клиентский скоринг: решение считает только сервер.
- Плашка на экране проверки: «Сейчас ход за: вами / специалистом банка / проверяем автоматически».

## 5. Запрос документов, варианты оферты, график

- `POST /api/applications/{id}/documents` (multipart: `kind`, `file`) — PDF/PNG/JPEG ≤ 10 МБ, хранение в volume, в БД путь/размер/sha256. Когда загружены все пункты чек-листа → заявка сама возвращается на `CHECKING_FNS`.
- **Варианты контрпредложения** (`decision.variants[]`, до 3): та же сумма на более длинный срок (если помещается), меньшая сумма на тот же срок (как сейчас), другой продукт. `accept-offer {variant_id}` — условия варианта становятся условиями договора.
- **Подсказка «что изменить»** (`decision.what_if[]`): пересчёт для максимального срока продукта и суммы −30%; показывать, если исход становится лучше.
- `GET /api/applications/{id}/schedule` — аннуитетный график после подписания; таблица на экране «Кредит выдан».
- `POST /api/applications/{id}/cancel`; фоновая задача переводит просроченные оферты и запросы документов в `EXPIRED` (сроки в env).
- Лента: контекст по статусу — `counter_offer`, `info_requested`, `approved`, `disbursed` (+ существующий `rejected`), по 1 синтетической статье на контекст.

## 6. Инфраструктура и надёжность (критерий «Enterprise»)

- **PostgreSQL 16** в `docker-compose.yml` (healthcheck `pg_isready`, volume). SQLite оставить для тестов.
- **Alembic**: первая миграция = вся схема; `alembic upgrade head` в CMD контейнера перед uvicorn.
- **Таблица `external_checks`**: каждое обращение к источнику — попытка, успех, ошибка, длительность. Таймаут + 2 ретрая внутри этапа.
- **Решения со снимком**: `decisions.inputs_snapshot` (всё, что пришло из источников), `policy_version`, `decided_by`, `confirmed_by`. Прежние решения сохраняются (`is_current = false`).
- **Демо-пульт**: `GET/POST /api/demo/failures {egrul|fns|bki: ok|slow|down}` — переключатели в тёмной полосе интерфейса, без пересборки. Только при `DEMO_MODE=true`. `demo/reset` сбрасывает и режимы сбоя.
- **Дашборд**: `GET /api/bank/dashboard` — заявки по статусам, доля автоматических решений, исходы, топ причин отказа, среднее время до решения, просроченный SLA. Экран `#/dashboard`.
- В `REVIEW_NOTES`: как масштабировать (очередь задач + воркеры, outbox, несколько реплик API).
