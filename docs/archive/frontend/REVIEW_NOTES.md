# Заметки для ревью (фронтенд)

## Что смотреть в первую очередь

| Файл | Что внутри |
|---|---|
| `frontend/src/api/scoring.ts` | Скоринг, ставка, решение, причина отказа — строго по `docs/SCORING_SPEC.md` |
| `frontend/src/api/scoring.test.ts` | Три эталона SPEC (97 / 46 / 8) и границы; платежи сверены независимым расчётом на Python Decimal |
| `frontend/src/api/stateMachine.ts` | Таблица допустимых переходов статусов |
| `frontend/src/api/mockApi.ts`, `mock/mockPipeline.ts` | Мок-сервер с той же логикой и теми же ошибками, что у бэкенда |
| `frontend/src/features/calculator/marginMath.ts` | «Запас прочности»: доля платежей в выручке и прогноз решения |
| `docs/openapi.yaml` | Контракт API, по которому работают оба клиента |

## Архитектура

- React 18 + TypeScript + Vite 7, Tailwind CSS 4, без роутера. Состояние — `useReducer` + Context (`src/state`), шаг и id заявки сохраняются в `localStorage`.
- Слой API — один интерфейс `CreditApi` (`src/api/client.ts`) и две реализации: мок (`VITE_USE_MOCK=true`, данные в браузере) и HTTP-клиент к FastAPI (`VITE_USE_MOCK=false`, запросы на `/api`). Экраны не знают, какая реализация работает.
- Конвейер проверок двигает сервер (или мок), интерфейс только опрашивает `GET /applications/{id}` раз в 700 мс (`state/usePollApplication.ts`). Мок вычисляет этап по времени с момента отправки, а не по таймерам, поэтому заявка продолжает путь после перезагрузки страницы. Это повторяет поведение бэкенда: он дозапускает застрявшие заявки при старте.
- Отправка заявки идемпотентна: один `Idempotency-Key` на одну попытку, двойной клик не создаёт дубль.
- Docker: сборка на `node:22-alpine`, раздача `nginx:1.27-alpine`; nginx проксирует `/api` на `backend:8000` через переменную и resolver, поэтому контейнер фронтенда стартует и без бэкенда.

## Допущения и упрощения

- Деньги — целые рубли, округление half-up (как `Decimal ROUND_HALF_UP` у бэкенда; в JS добавлен допуск 1e-9 против ошибок float).
- Факторы скоринга для экрана округлены до 0,1 балла, итоговый балл — сумма неокруглённых факторов, округлённая до целого (как в SPEC).
- При отказе со score < 45 ставка не определяется (`rate = null`), платёж и сумма не показываются.
- Кредитную историю в демо задаёт пользователь в карточке компании; в реальном процессе она приходит из БКИ. Это отмечено подсказкой у поля.
- Клиентской авторизации нет: история заявок общая для демо. Роль сотрудника банка — отдельный экран по токену (`X-Bank-Token`), в планах.
- Дата повторной подачи — сегодня + 3 календарных месяца; если такого числа нет, берётся последний день месяца.

## Что смоделировано

ЕГРЮЛ (синтетический реестр из 5 компаний), БКИ (кредитная история из карточки, режим сбоя `VITE_MOCK_BKI_FAILURE=true`), скоринг (правила SPEC), подписание (код 1234 показан в окне — SMS запрещены условиями кейса, 5 попыток), выдача (смена статуса через 1 с). Материалы ленты — синтетические советы без ссылок на законы и реальные компании.

## Отступления от брифа и почему

- **Node 22 вместо 20.** Поддержка Node 20 закончилась в апреле 2026; последний совместимый с ним Vitest 3 содержит критические уязвимости. С Node 22 `npm audit` — 0 уязвимостей.
- **Лента под шагом, а не боковой колонкой.** Справа стоит карточка «Ваша заявка»; лента ниже — главная статья и список, так её лучше видно на демо.
- **Вместо «Шаг N из 4» — карточка «Ваша заявка».** Пользователь заполняет только два экрана, проверку и решение делает банк; карточка показывает путь вместе с уже введёнными данными.
- **Добавлен «Запас прочности».** Шкала доли месячной выручки, которую займут кредиты, линия безопасного предела 25% и прогноз решения ещё до отправки. Прогноз считается тем же `evaluate()`, что и решение, поэтому всегда с ним совпадает.

## Ограничения и развитие

- Прогноз в калькуляторе честен только для данных, которые ввёл пользователь; банк перепроверяет их в ЕГРЮЛ и БКИ.
- Опрос раз в 700 мс прост и надёжен для демо; для нагрузки — Server-Sent Events или WebSocket с тем же контрактом.
- Следующий шаг — рабочее место сотрудника банка: очередь заявок, автоматический расчёт нагрузки и лимита, сценарии «что если» и автоматическое заключение.
